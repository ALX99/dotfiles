# Repository Map

## Repository Purpose

This Stow-managed personal repository holds shell tooling, desktop applications, system setup, and AI-agent configuration. `.local/`, `home/`, and `.config/` are packages installed into `~/.local`, `~`, and `~/.config`; `.stowrc` deliberately disables Stow folding.

## Architecture and Ownership

- `.local/bin/` owns user executables. `home/` owns configuration, including Bash, SSH, Git, and agent files. Start shell changes at `home/.profile`, `home/.bashrc`, and `home/.bashrc.d/`.
- `.config/` owns application configuration. Neovim starts at `.config/nvim/init.lua`; compositor, terminal, and other desktop settings live beside it. Karabiner's JSON is generated from `misc/karabiner/karabiner.cue` into the tracked `misc/karabiner/karabiner.json`, and `mise run install` copies it to `~/.config/karabiner/karabiner.json` when that path is absent; Karabiner rewrites the installed file itself, so it is copied once rather than stowed as a link its writes would dirty. Herdr plugins share CLI execution and validated workspace fields through `.config/herdr/plugins/_shared/herdrlib.py`; each plugin owns its Git or installation policy.
- `misc/` owns Arch, systemd, pacman-hook, and keyboard assets. `.devcontainer/` defines the Arch development environment rather than the installed host configuration.
- `home/.agents/skills/` contains harness-independent skills. Pi-specific settings, prompts, themes, and skills belong in `home/.pi/agent/`; do not put Pi-only material in the shared skill tree. `home/.pi/agent/settings.json` owns local Pi defaults and external package registrations.
- `home/.pi/agent/extensions/` is a strict TypeScript/NodeNext package. The package has one root `index.ts`; `src/application.ts` owns named Effect workflows, `src/runtime.ts` the per-session ManagedRuntime, and `src/pi/adapter.ts` the lifecycle boundary. `src/pi/adapters/` composes cohesive Work, ModelContext, ToolExecution, tools, presentation, and host integrations; the Pi adapter owns their shared runtime, tool selection, provider workflow, activity projection, and settlement decision. Work coordinates task, rescued-input, schedule, and recovery behavior; ModelContext sequences prompt visibility and provider transforms; ToolExecution installs one observer for all tools whose renderers share duration state. Feature modules own domain rules and durable state, while their cross-feature lifecycle is coordinated by these application-owned adapters. `src/**/tests/` owns coverage. Effect is the extension idiom: it owns I/O, concurrency, lifetimes, and error channels, while pure parsing, validation, state transitions, and rendering stay synchronous. `src/support/fs.ts` is the only module allowed to import `node:fs` and exports Effect-returning functions directly. The application ManagedRuntime is the bridge for session-scoped workflows and injected feature I/O; `src/support/effect-runtime.ts` remains for process-lifetime host work and low-level support tests, and `src/support/errors.ts` owns `FsError` and caught-value narrowing (`toError`, `hasNodeErrorCode`). Feature failures retain their own error channels. Durable state stays in feature-owned session-entry replay, transient work stays in the session runtime, and application workflows cross Pi boundaries through ManagedRuntime. `src/host/process-reaper.ts` owns session-scoped Bash process-group markers and cleanup for agent-started background descendants; `src/pi/adapters/host.ts` binds its typed tool and shutdown handlers alongside title lifecycle handlers. `src/tasks/` owns task queues (one to 100 tasks, including discovery tasks that add follow-ups) with per-task checkpoints and chained branch-summary compaction of completed task traces: `state.ts` owns the queue model, session-log replay, and transitions without Pi APIs, `register.ts` owns task capability registration and produces typed lifecycle handlers; `src/pi/adapters/work.ts` binds those handlers and coordinates task work, checkpoint navigation, and status projections, `tools.ts` the model-facing schemas, and `dashboard.ts` the read-only UI. `src/context/skills/` owns `/skills` discovery, validation, token accounting, and pre-first-turn model-visibility selection while preserving Pi's native `/skill:name` expansion; `src/context/skills/state.ts` reads the validated branch selection, and `src/context/system-prompt/systemprompt.ts` is its only prompt renderer. `src/agents/` owns profile discovery and immutable snapshots, the active root-session profile/policy source, shared capability policy, persistent child sessions, parent-scoped registry/mailbox state, invocation workflows, and observable activity inspection; `src/pi/adapters/agents.ts` binds profile-switch commands and agent workflows/tools to parent and headless child sessions, while ModelContext reads the selected profile prompt and skill policy dynamically. Spawned child profiles remain immutable snapshots. Each agent's conversation remains a normal Pi JSONL session, while orchestration metadata and unconsumed events live in the parent-session registry. Mailbox events are persisted before notification and surfaced at safe points; lifecycle events describe invocation outcomes only, not task completion or progress. `src/tools/ask-question/` and `src/tools/apply-patch/` own their corresponding tools. `src/openai/compaction/` runs OpenAI's own Responses compaction alongside Pi's: it asks the API for its encrypted replacement history at Pi's compaction boundary, keeps that history in the compaction entry's `details.remoteCompaction` beside Pi's own summary, and replaces the input of later requests for the same model with it. The session file is its only state, so a fork, a navigation, and a restart replay the same history. Pi's native session projection owns context edits, custom messages, and branch summaries; its exported Responses serializers own message and tool conversion, including grammar tools. `pi-responses.ts` isolates loading those exported modules around Pi's jiti subpath alias, verified through the native extension loader. A newer Pi-only compaction supersedes an earlier encrypted checkpoint. Pi owns every transport, including the Codex WebSocket one, so the extension adds no provider of its own. API-key and Codex sessions use the explicit compaction-trigger protocol; direct OpenAI OAuth sessions use Responses context management, keeping only its leading encrypted compaction item and discarding subsequent generated output. The protocol is derived from the session's model and credential at the compaction boundary; failures leave Pi's own summary in use. `src/openai/search/` owns hosted `web_search` injection for OpenAI Responses providers, its `~/.pi/codex-web-search.json` config, and typed stream/recall handlers; `src/pi/adapters/model-context.ts` owns their Pi subscriptions and request sequencing, feeding the search transcript entry on every transport. Those entries are TUI-only, and a search reaches the model only through the server-side response chain Pi continues across requests, so `recall.ts` decides which recorded searches the model can still reach: a compaction rewrites the input that chain hangs off, and any other change to the request body makes Pi start a new chain. `src/openai/search/register.ts` marks the branch's earlier records unreachable at each prompt, exposes `web_search_log` only while such records exist, and injects a manifest of their queries and source hosts — never the URLs, which stay in the record — naming the tool or, when the session's selection excludes it, the session file. `src/ui/copy-code.ts` owns code-block clipboard selection; `src/context/nested-instructions/nested-context.ts` owns subtree instruction discovery and produces typed lifecycle/tool-call handlers; `src/pi/adapters/model-context.ts` owns the subscriptions that invoke them when tools touch files below the session working directory. `src/host/caffeinate.ts`, `src/automation/model-shortcuts.ts`, `src/automation/interrupt-on-empty-enter.ts`, `src/automation/retry.ts`, `src/automation/schedule.ts`, and `src/host/title.ts` own host integrations; `src/ui/statusbar.ts` owns its metrics and presentation behavior and returns typed lifecycle handlers that `src/pi/adapters/presentation.ts` subscribes; `src/ui/compact.ts` registers renderer-only overrides for builtin bash, edit, and read rows, preserving native execution and delegating expanded read output through Pi's renderer chain. `src/support/tool-status.ts` owns shared animation and execution-event timing logic, initialized once by `src/pi/adapters/tool-execution.ts` for builtin tools and Apply Patch. Animation loops run through the session ManagedRuntime and stop on result, navigation, or shutdown; timings persist as `tool-duration` custom session entries and replay from the active branch. `src/support/change-render.ts` owns the right-aligned duration column; `src/context/system-prompt/systemprompt.ts` owns the replacement system prompt and its `/systemprompt` viewer, rebuilding the prompt from the live tool registry so the advertised tools and their guidelines never drift from the enabled set, and listing the tools `codemode` moved behind its own tool separately from the ones the model calls itself.

## Key Flows and Sources of Truth

`mise run install` restows the three user packages and links shared skills; it can change `$HOME` and enable the user `ssh-agent`. `mise.toml` owns the bootstrap manifest and tools; `.mise/tasks/` owns automation as standalone scripts (entry points flat, subsystem work namespaced like `pi:check` and `karabiner:check`, generators inverted as `gen:<area>` and run together by `mise run gen`). Together they are the source for installation and host setup. GitHub Actions installs the tools from `mise.toml` and runs `mise run check` for every push and pull request.

Across Pi extensions, prompt hooks run in chain order and the last writer wins. The personal extension's ModelContext workflow rebuilds its prompt and search recall manifest from Pi's live tool selection, including CLI constraints and custom-tool activation, then applies hosted-search and compaction-history transforms in order. Skill visibility derives from native branch entries and the supplied inventory; no selection mirror or separate durable state is kept. The enabled skill names serve both `/skills` and prompt rendering. `src/host/process-reaper.ts` owns a process-local group registry; its temporary marker files only hand PIDs from Bash to that registry and are not durable session state.

`.openai-server-compaction.json`, read from `~/.pi/agent/` and then `.pi/` with `PI_OPENAI_SERVER_COMPACTION_ENABLED` as its only environment override, is the only configuration `src/openai/compaction/config.ts` reads. Its replacement history is model-scoped and read back from the branch, so none of it lives in memory: a switch, fork, navigation, or restart replays exactly what the session recorded, and a model that never compacted replays nothing.

The tasks extension's model-facing protocol is intentionally limited to `create_tasks` with plain task titles and `finish_task` with a status, outcome, and optional `addTasks` placements. After checkpoint compaction, hidden `tasks:continue` custom messages trigger model continuation with the next task title (or request a final summary); a hidden `tasks:reminder` custom message asks for the current task's outcome when the agent settles with it still pending, at most once per task, and never in headless mode, while deferred user input is being replayed, or after a turn the user interrupted or that failed; user-facing active-task status shows progress separately, while stable IDs remain in tool results and checkpoint data. A task boundary may be nested in a codemode script only as its sole nested tool call; the enclosing codemode result carries durable queue/outcome details for replay, and successful nested edits carry their observed paths into later task outcomes. In TUI mode, `/tasks` opens a read-only dashboard with queue/task navigation and scrollable recorded outcomes, changed files, and discovered tasks; `/tasks status` keeps the concise notification. Dashboard history and execution share the same validated branch-entry replay, including completed queues, without adding model tools or separate persistence. Existing tasks are monotonic from the model's perspective: additions are atomic with outcomes, while IDs are generated by the plugin and exposed only as stable queue references; additions may target the current task, the queue end, or an existing pending task, while file attribution, checkpoint lifecycle, replay, and human cancellation remain plugin bookkeeping, with no model-facing task history or destructive queue mutation tool.

Nested context restores on branch navigation and uses native steering so instructions reach the next model step.

## Where to Start

- For user commands or shell behavior, inspect `.local/bin/` and the `home/` shell file.
- For an application or desktop change, begin under `.config/`; follow related Colemak-DH mappings across affected applications.
- For Karabiner changes, edit `misc/karabiner/karabiner.cue`, then run `mise run gen:karabiner` and `mise run karabiner:check`; copy `misc/karabiner/karabiner.json` over `~/.config/karabiner/karabiner.json` to apply a regenerated config to an existing install.
- For Twilight Bloom changes, edit `misc/themes/twilight-bloom.cue`, then run `mise run gen:theme` and `mise run theme:check`. It generates Ghostty, Herdr, and Pi themes.
- For system provisioning or keymaps, begin at `misc/` and `mise.linux.toml`. Do not casually run `MISE_ENV=linux mise bootstrap` or the `linux-system` task; they make privileged host changes.
- For Pi behavior, begin at the relevant extension entry point and its tests. Run `mise run pi:check` for extension changes; use `bash -n home/.bashrc home/.profile` for shell changes.

## Critical Constraints

Keep tracked links as links: `CLAUDE.md` targets this file, `home/.bash_profile` targets `.profile`, and the Claude/Codex instruction links lead to `home/.pi/agent/APPEND_SYSTEM.md`. Extensions require Node 26+, pnpm, tabs, and `oxfmt`; the Pi packages follow the host Pi release line through caret ranges, while `effect` is pinned to the 4.0.1 stable release. `mise run pi:deps` installs the dependency set into both the repository tree and `$HOME/.pi/agent/extensions`, because Pi resolves extension imports through jiti from that installed directory. `home/.pi/agent/settings.json` enables the built-in `codemode` tool with `codemode.mode: "on"`, keeping active direct tools callable while allowing the model to use codemode scripts. Validation and domain modeling use Effect `Schema`. Errors that type an Effect or `Result` channel are `Schema.TaggedError` classes carrying a `message` field, because `runPromise` rejects with the error itself; failures whose message is the entire contract, such as tool argument and input validation, stay plain `Error`s thrown at that boundary. Do not reintroduce `zod` or `neverthrow`: pure parsers return Effect `Result`, and only Pi tool parameter schemas use `typebox`. Keep the package manifest, lockfile, workspace policy, and `src/tools/apply-patch` grammar synchronized when upgrading those packages. The tool vendors Codex's `apply_patch` Lark grammar, keeps a test that checks it against the installed `codex` binary, and activates `apply_patch` for models whose `compat.supportsOpenAIGrammarTools` flag makes the provider emit OpenAI custom grammar tools, without disabling Pi's `edit` or `write` tools. Colemak-DH navigation is coordinated across Nvim, tmux, Sail, keyd, Karabiner, Ghostty, and readline. `misc/themes/twilight-bloom.cue` is the source of truth for the Ghostty, Herdr, and Pi light/dark themes; the generator preserves Ghostty's ANSI palette and explicitly maps UI-only surfaces for Herdr and Pi. Bash PS1 and LS_COLORS consume the Ghostty ANSI palette directly. Pi picks the generated pair through its `light/dark` theme setting, and `pi --export` renders before theme setup so it stays on the built-in theme. GNU tools come first in PATH on macOS through `home/.profile`, so non-interactive shells and coding agents get GNU cat, sed, find, grep, and tar; call those plain names in scripts instead of g-prefixed ones or BSD fallbacks, and keep g-prefixed aliases out of `home/.aliasrc`.

## Maintenance

Keep this repository map current. When a change adds, removes, or relocates a major subsystem; changes an architectural boundary or source of truth; or introduces a critical repository-wide constraint, update `AGENTS.md` in the same commit. Do not record routine implementation details or file-level churn.

# Learning More About Effect

The Pi extensions use the Effect TypeScript library.

Before writing any Effect code, first read `home/.pi/agent/extensions/node_modules/effect/AGENTS.md` **completely**, and follow the links in the file when required.

If you need to learn more about particular Effect apis and concepts that the guide doesn't cover, search through the source code in `home/.pi/agent/extensions/node_modules/effect/src`.
